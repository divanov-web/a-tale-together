# Интерпретатор

Текст заявки → намерение по [каталогу действий](../game/actions.md). Не решает, не бросает, не создаёт.

## Схема ответа
Один вызов на раунд после дедлайна: вход — сцены с заявками всех персонажей, выход — массив намерений по `model.Intent` (решение руководителя 2026-10-10).
```json
{
  "intents": [
    {
      "submission_id": 41,
      "action_type": "interact",
      "target": "cellar_door",
      "approach_idx": 1,
      "push": false,
      "ambiguities": []
    },
    {
      "submission_id": 42,
      "action_type": "interact",
      "target": "",
      "attribute": "agility",
      "skill": null,
      "risk": "hard",
      "on_success": {"fact": "Ров преодолён: на другом берегу видна тропа к башне."},
      "on_fail": {"condition": "wounded"},
      "push": true,
      "ambiguities": []
    },
    {
      "submission_id": 43,
      "action_type": "explore",
      "target": "",
      "ambiguities": ["два сундука: у окна и у двери"],
      "fallback": {"action_type": "explore", "target": "chest_window"}
    }
  ]
}
```
- `action_type` только из каталога; неизвестное → `ambiguities` + `fallback`.
- `target` — ключ видимого объекта, имя выхода или никнейм персонажа из переданного контекста; пустой — действие в локации.
- Подход объекта (`approach_idx`) предпочтительнее свободного испытания: сложность и эффекты берутся из данных локации.
- Свободное испытание: `attribute` и `skill` из модели персонажа, `risk` (`normal / hard / extreme` → 1 / 2 / 3 успеха, число успехов назначает код), эффекты обеих ветвей заранее из списка: `fact` (знание персонажа), `condition` (состояние), `move` (выход), `reveal` (объект), `damage` (в лимите режима). Изменение состояния объектов — только через подходы из данных локации.
- `push` — игрок готов рисковать (форсировать бросок). Цепочка действий → первое действие, остальное в `ambiguities` с пометкой `extra`.
- Заявка без `attribute` и подхода, не `move`/`wait`/`help`/`explore` — безопасное толкование.

## Жизнь свободного действия
1. Игрок: `/act перепрыгиваю ров с разбега, чтобы попасть к башне` — текст лежит в заявке как данные до дедлайна.
2. Дедлайн: снимок раунда; все заявки, и выбранные из предложенных подходов, и свои, уходят в один вызов интерпретатора вместе с контекстом сцен (решение руководителя 2026-10-10); разбор кодом только при сбое модели.
3. Интерпретатор назначает до броска: `interact`, Ловкость, риск `hard`, `on_success` — факт «ров преодолён, тропа к башне», `on_fail` — состояние «ранен», `push` по тексту.
4. Код валидирует: характеристика и навык есть в модели, цель видна, риск из таблицы, эффекты из списка. Невалидно — повтор, затем `fallback` или `wait`.
5. Движок: сложность = таблица риска (2) + сложность локации; пул по персонажу; бросок по seed; форсирование по `push` и режиму. Выбирается ветвь: события `check_rolled` и `fact_learned` при успехе, `condition_added` при провале. Снимок и seed позволяют воспроизвести.
6. Рассказчик (второй и последний вызов раунда) получает события и пишет хронику; исход и факты он не меняет.
Модели не нужен отдельный вызов «после броска»: последствия обеих ветвей заданы до броска, а их описание — задача рассказчика.

## Контекст вызова
По локациям из снимка v2: персонажи сцены (ID, никнейм, краткие характеристики, состояния, знания), видимые объекты с подходами и их названиями, видимые выходы, каталог действий; заявки всех персонажей раунда в одном выделенном блоке данных. Скрытые объекты, скрытые выходы и чужие секреты не передаются.

## Валидация
JSON-схема → проверка ID и типов движком → невалидно: один повтор с ошибкой в промпте → `ambiguous` с безопасным толкованием (`fallback`, иначе `wait`; решение руководителя 2026-10-10, G3). Один вызов на все заявки раунда после дедлайна; уточняющих вопросов игроку нет.
