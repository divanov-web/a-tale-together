# 09а. Журнал чатов для отладки

- Статус: план
- Этап концепта: 2
- Зависит от: 02, 05, 06, 09

## Цель
По каждому чату (группа игры и личка игрока) ведётся файловый журнал, который читает ИИ при разборе ошибок: входящие сообщения игроков, исходящие сообщения бота, вызовы LLM с полным входом и выходом, события раунда с причинами. По журналу восстанавливается весь обмен без доступа к БД; по нему ищутся баги алгоритма раунда и промптов. Сейчас есть только `logs/bot.log` (структурные записи без текстов) и `llm_runs` (метрики вызовов без промптов и ответов).

## Критерий готовности
После раунда в песочнице в `logs/chats/<telegram_chat_id>/` лежит журнал, из которого ИИ без БД восстанавливает: каждое входящее сообщение (кто, что, команда), каждое исходящее (текст, `outbox_id`, `part`, `telegram_message_id`), каждый вызов LLM (роль, версия промпта, раунд, вход, выход, ошибка, токены, дозапрос), события раунда (открыт, заморожен, пропущен с причиной, разрешён, опубликован). Записи личек ссылаются на `game_id`, записи игры — на группу; дубли update помечены, а не потеряны. Журнал выключается конфигом; `make test` и `make lint` зелёные.

## Решения (безопасные допущения, уточняются ADR при реализации)
- Формат: JSONL, файл на день `logs/chats/<telegram_chat_id>/YYYY-MM-DD.jsonl`; одна запись — одна строка с полями `ts`, `kind` (`in | out | llm | round | error`), `update_id`, `game_id`, `round_id`, `round_no`, `user` (Telegram ID и никнейм), `command`, `text`, для `llm` — `role`, `prompt_version`, `attempt`, `request` (системный промпт и вход), `response`, `error`, `tokens_in`, `tokens_out`, `duration_ms`; для `out` — `outbox_id`, `part`, `telegram_message_id`. Многострочный текст в JSON-строках, чтобы `grep` по `round_no` и `update_id` работал построчно.
- Точки записи: входящее — `app/bot.Handle` сразу после разбора update (до дедупликации, дубль помечается `duplicate: true`); исходящее — обёртка над `adapter/telegram.Client.SendText` (покрывает ответы бота и воркер outbox) плюс `app/delivery` дописывает `outbox_id`, `part`, `telegram_message_id`; LLM — `app/llm.Complete` (вход и выход каждой попытки, в том числе дозапросы интерпретатора и рассказчика); раунд — `app/round` (open, freeze, skip с причиной, resolve с итогами заявок и замечаниями проверки рассказчика, publish).
- Адресация: вызовы LLM и события раунда пишутся в папку группы игры (`games.chat_id` → `chats.telegram_chat_id`); личные сообщения — в папку лички с полем `game_id`, если игрок состоит в игре.
- Писатель — новый адаптер `adapter/chatlog`: создаёт папку лениво, пишет с мьютексом без `fsync`, ошибка записи только в `slog`, игровой сценарий не ломает. В приложения отдаётся узким интерфейсом (`Journal`) с фейком для тестов. Конфиг: `CHAT_LOG_DIR` (по умолчанию `logs/chats`, пусто — выключено), `CHAT_LOG_RETENTION_DAYS` (по умолчанию 30, удаление старых файлов при старте).
- Приватность: журнал содержит тексты игроков и `secret_bio` во входе рассказчика, поэтому только локально (`logs/` в `.gitignore`), токен бота и ключи не пишутся никогда; включение на проде и срок хранения — решение в пункте 11.

## Проверка
Юнит-тесты адаптера (папка на чат, файл на день, многострочный текст, ошибка записи не останавливает сценарий) и сценариев с фейком журнала; раунд в песочнице с 3 персонажами: по `grep` `round_no` в папке группы видны вход и выход интерпретатора и рассказчика, хроника с `telegram_message_id`, в папках личек — `/act` игроков и уведомления о заявках.

## Открытые вопросы
Хранение журнала на проде и срок (пункт 11); нужен ли экспорт раунда в один файл для разбора (`/debug round N` dev-команда пункта 10, шаг 6).
