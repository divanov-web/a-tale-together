# A Tale Together: динамическая генерация мира и квестов

- Дата: 12 октября 2026 года.
- Статус: оценка и предлагаемый план; принятые правки и план — [динамический мир](../game/world.md), пункты 27–31 плана бота (2026-10-12): три таблицы объект/предмет/NPC сохранены, этапы квестов привязываются лениво, генерация только в вызове рассказчика, порядок пунктов перекроен под играбельный срез.
- Исследованное состояние: [master, 955c3fe](https://github.com/divanov-web/a-tale-together/tree/955c3fe591bac81c70f9330b79f29e3bb2a0be5f).
- Объём: карта по координатам, постоянные сущности, цели фракций, квесты, влияние игроков, контексты и токены, восемь предлагаемых пунктов плана.

## 1. Оценка предложения

Предложение подходит для текстовой Telegram RPG с приоритетом вариативности. Пространственная сетка, ограниченные активные квесты и создание деталей при посещении позволяют увеличивать мир без передачи всей истории в каждый запрос. Наибольшая сложность — связь новых сущностей со свободными действиями, прогрессом квестов и сохранением после ошибок.

| Часть | Сложность | Оценка |
|---|---|---|
| Сетка и четыре направления | низкая | библиотека генерации карты для первой версии не требуется |
| Короткие карточки соседей и подробности при входе | средняя | нужны постоянные идентификаторы и стадии подготовки содержимого |
| NPC, переносимые предметы, квесты в БД | средняя | базовое хранение уже есть, самостоятельные сущности потребуется добавить |
| Цепочки квестов, лимиты и выдача по исследованию | средняя | счётчики, условия и переходы полностью считает код |
| Новые способы решения по свободному тексту | высокая | требуется расширить интерпретатор, эффекты и связывание с этапами квеста |
| Несколько групп и противоборствующие фракции | высокая | один общий мир, различные интересы, общий прогресс и отсутствие дублирования |
| Контекст, повторы и отказоустойчивость | средняя–высокая | локальность нужна также в SQL и снимках, не только в промпте |

Грубый плановый ориентир полного описанного прототипа: 24–40 рабочих дней одного backend-разработчика, знакомого с проектом, включая тесты и интеграцию, с ИИ как помощником. Это оценка объёма, не замер производительности и не обязательство по сроку. Понадобится пересчитать после первого вертикального среза. Новый интерфейс карты, изображения, боевой PvP и симуляция всех NPC вне сцены в оценку не входят.

| Генерация при старте | `Opening` возвращает только текст завязки на основе готовых локаций | заменить контракт на стартовый пакет мира и текст |
| Рассказчик | `narrator/v3`, только `{chronicle, scenes}`; новые сущности создавать запрещено | новая версия контракта с проектами содержимого и отдельным приёмом кодом |
| Контексты | оба LLM получают занятые сцены; рассказчик получает завязку и обрезанные общие тексты трёх раундов | добавить короткую память по постоянным сущностям и квестам |
| Снимки | `ListLocations` загружает все локации мира в снимок каждого раунда | для растущего мира заменить локальным снимком и адресной загрузкой зависимостей |
| Восстановление | ADR-0013: повтор всего раунда после отката, LLM внутри транзакции | при сложной генерации сохранять пригодные результаты вызовов отдельно, чтобы не оплачивать повторное создание |

Важные ограничения кода: выходы сейчас сопоставляются по названиям; новая неизвестная цель взаимодействия отклоняется интерпретатором; `saveState` сравнивает локации по позициям в срезе и обновляет только JSONB объектов. Динамическое добавление локаций требует сохранения по ID, операций создания и обновления, и изменения воспроизведения.

## 3. Карта: геометрия в коде, содержимое у ИИ

### 3.1. Достаточный алгоритм

- Старт: `(0,0)`.
- Соседи: `(x+1,y)`, `(x-1,y)`, `(x,y+1)`, `(x,y-1)`.
- Координаты и допустимые направления определяет код.
- Уникальность: `(game_id, x, y)`; при разных картах сезона добавить идентификатор карты/сезона.
- Возврат загружает существующую клетку; содержимое повторно не генерируется.
- Название — подпись, не идентичность клетки. Для одноимённых лесов и пещер потребуется пересмотреть нынешнее ограничение `UNIQUE(game_id,name)`.
- В первой версии все четыре геометрических перехода доступны; непроходимые границы, реки и мосты добавить после устойчивого первого среза. Если такие границы вводятся сразу, маршруты квестов нужно проверять по реальному графу проходимости.
- Тип крупной местности можно задавать дешёвой функцией от seed и координат региона, например блока 4×4 клетки. Это даёт локальную связность; ИИ добавляет детали и атмосферу. Крупная сетка является моделью перемещений, а не реалистичной картой местности.

Для начальной сетки не нужны WFC, поиск библиотек картографа или отдельная модель ИИ. Когда геометрия уже задаётся программой, роль LLM остаётся смысловой: что находится в разрешённой клетке.

### 3.2. Три различимых состояния

| Состояние | Что хранится | Что известно игроку |
|---|---|---|
| Не подготовлена | координаты и стабильный ID/адрес | ничего или только направление |
| Короткая карточка | тип местности, название, описание 1–2 предложениями | например, «на севере лес и дым за деревьями» |
| Подготовлена подробно | объекты, подходы, NPC, факты, привязанные этапы квестов | содержимое раскрывается по посещению и действиям |

Посещение хранится отдельно от стадии подготовки. Созданная соседняя клетка ещё не считается открытой для счётчика исследования. Для прототипа можно считать посещение и раскрытие общими для мира; персональное или фракционное знание — отдельное расширение.

Если игрокам уже показали название, направление и заметные признаки клетки, эти данные сохраняются. Подробности при входе должны им соответствовать. Не показанные детали остаются свободными для дальнейшей генерации.

### 3.3. Старт и достройка

На старте создать пять клеток: подробную центральную и четыре короткие карточки соседей. Также подготовить цели существующих фракций и один общий сюжетный квест. Если требовать отдельный первый сюжетный квест для каждой фракции, стартовых сюжетных квестов будет два и изменится выдача по счётчику.

При движении запрашивать у ИИ только отсутствующие данные: подробности клетки, куда пришли, и короткие карточки недостающих соседей. При прямом движении без возвратов обычно возникают три новые соседние клетки, а не четыре: предыдущая клетка уже существует. После шести шагов по прямой подготовлено 23 геометрические клетки: начальные 5 плюс 6×3.

Соседние клетки желательно описывать коротко, чтобы ещё не исследованная часть мира могла учитывать действия игроков. Все четыре соседние клетки подробно генерировать заранее допустимо, но это дороже и раньше закрепляет будущий сюжет.

## 4. Контекст: полная история чата не нужна

Недостаточно передавать только четыре соседние клетки. Нужны текущая клетка, участники и события, короткие карточки соседей, активный этап квеста и несколько важных постоянных фактов.

| Блок | Детализация |
|---|---|
| Мир | жанр/тон, цели фракций, несколько опорных фактов |
| Текущие клетки групп | видимые объекты, состояния, присутствующие NPC, доступные подходы |
| Соседи | ID, координаты, направление, тип и короткое описание; без полного перечня скрытых вещей |
| Активные квесты | цель, текущий этап, ближайшая подсказка, уже выполненные этапы в одной фразе |
| Важный удалённый NPC/объект | короткая адресная карточка, когда он упомянут в действии или текущем квесте |
| Игроки | только данные, которые нужны соответствующей роли запроса |
| Недавние события | краткие структурированные результаты, не весь чат |

При четырёх разошедшихся группах объединение текущих клеток и их соседей может содержать до 20 различных клеток. Одна общая локация для нескольких групп не должна дублироваться в блоке географии; группы описываются отдельно. Соседние карточки остаются короткими.

Памятью должны служить сохранённые состояния и факты с ID, а не начало последнего художественного текста. Нынешняя выжимка рассказчика берёт максимум 400 символов из общего текста каждого из трёх раундов; истории отдельных сцен туда не входят. Такое обрезание полезно для стиля, но не хранит надёжно обещания NPC и прогресс квеста.

Для первой версии достаточно обычных SQL-запросов по ID сущностей, связям квеста, именам/алиасам и текущим координатам. Векторная БД и отдельный запрос на «вспомнить всю историю» не требуются. Память об изменениях важных NPC и выполненных этапах следует обновлять событиями; декоративные детали допускается забывать.

Локальность нужна на трёх уровнях: чтение из БД, снимок для движка, пакет для LLM. Если ограничить только промпт, прежний `ListLocations` продолжит копировать всю растущую карту в каждый раунд. Это создаёт рост объёма снимков и стоимости загрузки даже при постоянном числе токенов.

## 5. Сущности

Испытание и предмет выполняют разные роли. Сундук может содержать предметы и иметь несколько испытаний; монета может переместиться в инвентарь и затем к другому владельцу. Сохранить существующее разделение объекта и его подходов.

| Сущность | Минимум данных | Примечание |
|---|---|---|
| Клетка/локация | ID, координаты, стадия подготовки, местность, описание, версия | постоянное место |
| Объект мира | ID, location_id, тип, название, state, скрытие, версия | дверь, сундук, следы, алтарь |
| Подход/испытание | стабильный key, действие, характеристика, навык, риск/сложность, условия и эффекты | несколько подходов к одному объекту; можно оставить определение в JSONB |
| Переносимый предмет | ID, тип, свойства, location/container/owner, версия | необходима самостоятельная запись, если предмет можно передавать и перемещать |
| NPC | ID, имя/алиасы, location_id, состояние, роль, краткие отношения и сведения | без полной симуляции расписаний NPC на первом этапе |
| Цель фракции | faction_id, версия, формулировка, стадия, несколько условий прогресса | обычно без конкретной конечной клетки |
| Квест | ID, тип, связанные цели/фракции, состояние, текущий этап, краткое описание | существует в мире без кнопки принятия |
| Этап квеста | objective_key, условия завершения, prerequisites, координаты/адрес или нераскрытая привязка, состояние | может иметь несколько способов достижения |
| Факт/раскрытие | ID/ключ, связанные сущности, scope, краткая формулировка, версия | важные сведения и знания, доступные адресату |
| Состояние исследования | число новых посещённых клеток после сброса, состояние запроса нового квеста | полностью считается кодом |

Локации и объекты уже хранятся в БД: JSONB тоже является хранением в БД. Не нужно нормализовать каждое текстовое свойство. Самостоятельные таблицы нужны для сущностей с постоянной идентичностью, владельцем, связями или независимым изменением. Определения подходов и компактные свойства допустимо оставить JSONB.

«Ничего полезного» — результат осмотра, например `searched=true`, а не переносимый предмет. Повторный осмотр без изменения состояния не должен каждый раз вызывать генерацию находки. Новое событие, например приход NPC, может изменить содержимое явно.

## 6. Квесты: цепочка целей с альтернативными способами

### 6.1. Организация

- Начальный лимит: 2 сюжетных + 2 побочных квеста на весь мир. Это предлагаемое допущение для экономии; лимит на каждую фракцию или группу умножит объём.
- Лимит считать по активным квестам, включая скрытые/намеченные. Скрытая бесконечная очередь тоже тратит ресурсы при генерации и сопровождении.
- Один общий сюжетный квест может иметь разные последствия для фракций. Если каждой фракции требуется своя линия, заранее решить, разделяют ли они два сюжетных слота.
- Сюжетный: область действия в пределах 3–6 соседних клеток/переходов; побочный: 2–4. Уточнить для реализации, что считается длиной: число клеток цепочки и допустимое расстояние до каждой следующей цели. В первой версии использовать не более шести этапов и достижимость следующего этапа по доступному графу.
- При создании хранить краткий смысл всех этапов, но подробно материализовать ближайший этап. Для будущих этапов достаточно адреса/резерва и ограничения роли, без полной генерации NPC и предметов во всех клетках.
- Географию маршрута и выбор разрешённых координат проверяет код. ИИ генерирует сюжетное объяснение маршрута.

### 6.2. Пример гибкости

Цель этапа: получить печать стражи. Возможные подходы: открыть сундук, разбить сундук, убедить стражника отдать печать, найти обход к хранилищу. Завершение проверяет код по состоянию «предмет нужного типа у разрешённого участника», а не по факту, что рассказчик написал «этап пройден».

Игрок предлагает новый способ. Интерпретатор связывает его с существующей целью этапа и предлагает подход с предусловиями, риском и эффектами. Код проверяет доступность, рассчитывает исход и применяет эффект. Это даёт реальную вариативность без создания совершенно нового квеста на каждую заявку.

Для начала использовать простые условия: состояние объекта, владение предметом, получение факта, посещение клетки, состояние NPC. Произвольные выражения и код от ИИ не исполнять. Саму сюжетную связность условий оценивает генератор и тестовый набор; JSON-схема не доказывает смысловую правильность.

### 6.3. Отсутствие отказа

Лимит без отказа допустим в прототипе, если квест не остаётся навсегда заблокирован. Когда игрок разрушил объект или убил важного NPC, понадобятся альтернативный оставшийся подход или изменение ещё не завершённой части цепочки. Это восстановление квеста, а не кнопка «отказаться».

Не подгонять каждое действие к гарантированному успеху. Рыбалка может дать сведения от рыбака, если это соответствует интересам игрока и текущему квесту; любой выловленный предмет не должен автоматически становиться ключом ко всему сюжету. Сохранённые последствия действий и возможность осмысленного провала поддерживают доверие к миру.

### 6.4. Цели фракций

Цель вроде «восстановить влияние Ордена» может не иметь конечной точки. Менять её по значимым событиям и завершению глав, хранить версию и причину изменения. Выполненные этапы и уже опубликованные факты сохраняются; пересматриваются будущие связи и ещё не раскрытые этапы. Произвольная смена главной цели каждый раунд сделает прогресс непонятным.

## 7. Выдача новых квестов

Предлагаемая точная трактовка сброса: счётчик обнуляется после добавления нового квеста и после завершения существующего. В полном наборе из четырёх квестов исследования не накапливают запас для мгновенной выдачи после освобождения слота. Это допущение следует закрепить в правилах, поскольку в исходном предложении смешаны абсолютные номера клеток и счётчик после сброса.

|---:|---:|
| 1 | 1 |
| 2 | 2 |
| 3 | 4 |
| 4 | выдача запрещена лимитом |

При старте есть один сюжетный. При последовательном открытии по одной новой клетке дополнительные квесты появляются после суммарно 1, 3 и 7 новых клеток: интервалы 1 + 2 + 4. После завершения одного из четырёх остаются три и вновь нужны четыре новые клетки.

Правила:

1. Клетка считается новой при первом фактическом входе в неё, а не при создании карточки соседа. Стартовую `(0,0)` не включать в этот счётчик.
2. Возврат не засчитывается. Две группы в одной новой клетке дают одно открытие.
3. Счётчик относится к миру; события входа обрабатываются в стабильном порядке.
4. Тип нового квеста выбирается по свободным слотам. Стартовая последовательность может быть: сюжетный → побочный → сюжетный → побочный.
5. Если сюжетных не осталось, нужен новый сюжетный сразу, независимо от счётчика исследования. При сбое ИИ создать простой квест из шаблона, чтобы условие «сюжетный всегда есть» выполнялось.
6. Обычно генерировать не более одного нового квеста за раунд. Набранный порог отмечать запросом на генерацию; сбрасывать его после принятия результата, а не до вызова. При нескольких открытиях в одном раунде допустимо переносить оставшиеся открытия в следующий интервал, но это должно быть единым правилом, а не зависеть от порядка ответов ИИ.
7. Явный сброс после завершения квеста имеет приоритет над накопленным запасом. Если требовался другой смысл сброса, меняется только эта политика, не общая архитектура.

Квесты существуют и раскрываются автоматически через сюжет. Выдача и прогресс не требуют кнопки «взять квест». При этом полезна возможность посмотреть известные цели и их прогресс; новый экран или команда не являются условием первой реализации.

## 8. Влияние игроков на генерацию

| Действие игроков | Реакция системы |
|---|---|
| Выбирают направление | код создаёт нужные адреса карты, генератор развивает этот участок |
| Осматривают руины, ищут древности | интерпретатор возвращает краткие теги интереса; будущие свободные детали чаще относятся к руинам и тайнам |
| Решают силой, торгуются, подкупают | добавляются подходящие альтернативные подходы к текущим целям, меняются состояние и отношения |
| Меняют важные обстоятельства | события влияют на будущие этапы и версии целей фракций |
| Возвращаются в знакомую клетку | читаются сохранённые последствия; новые детали добавляются только явно |

Для памяти направления достаточно 1–2 тегов интереса из интерпретатора, нескольких последних результатов и краткого текущего намерения группы. Агрегацию голосов/действий группы, сроки и ограничения делает код. Не нужен отдельный вызов на анализ всей истории.

У мира должны оставаться независимые обстоятельства: ранее показанный лес сохраняется лесом. Игроки влияют на неизвестные детали, новые встречи, способы решения и последствия, а не переписывают произвольные уже известные сущности текстом заявки.

## 9. Конвейер LLM и вопрос картографа

### 9.1. Рекомендация: два обычных вызова

| Фаза | Работа ИИ | Работа кода |
|---|---|---|
| Перед разрешением | интерпретация заявок; при необходимости предложение нового локального подхода/сущности, связывание с этапом | локальный снимок, поиск существующих целей, проверка предложений и предусловий |
| Разрешение | модель не вызывается | d100, движение групп, изменения объектов, предметов, этапов и счётчиков |
| Подготовка следующей сцены и описание | один общий ответ: хроника и ограниченные проекты новых клеток, NPC, квестов/следующих этапов | составление конкретного задания на генерацию, разрешённых адресов и лимитов; приём предложений и событий |
| Публикация | дополнительных вызовов нет | фиксация принятых сущностей, текстов и outbox; видимость и последующие варианты действий |

Один вызов на все группы соответствующей роли, а не отдельный запрос на игрока, клетку, NPC или квест. При старте отдельный пакет `opening` вне раунда создаёт карту, цели, сюжетный квест и вступление.

Предложения о новом способе решения нужны до броска: если генерировать только после рассказчика, новая заявка сможет повлиять на мир лишь в следующем раунде. Применённые предложения и эффекты записываются, чтобы replay не обращался к модели.

### 9.2. Отдельная роль генератора

Самостоятельный генератор содержимого имеет смысл как программный интерфейс и режим промпта. Ему не обязательно соответствовать дополнительный запрос в каждом раунде. Отдельный вызов по событию допустим, если совмещённый ответ ухудшает качество или таймауты: одна пачка на старт/достройку/новый квест, с сохранением результата. Не использовать отдельную ИИ-роль для вычисления координат.

Третий вызов не всегда дороже в сумме: специализированный компактный вход может оказаться дешевле чрезмерно сложного общего промпта и повторов. Для проекта сначала сравнить две схемы на одном наборе случаев: токены, задержка, частота исправлений, качество новых подходов. Стартовое допущение — два обычных вызова, отдельный генератор выключен.

### 9.3. Новые факты и художественный текст

Новый ответ должен разделять текст и структурированные предложения. Пример формы:

```json
{
  "chronicle": "Общий текст",
  "scenes": [{"scene_id": 1, "text": "Текст сцены", "event_seqs": [41]}],
  "proposals": {
    "cell_details": [],
    "neighbor_cards": [],
    "objects": [],
    "npcs": [],
    "quests": [],
    "quest_links": []
  }
}
```

Это эскиз контракта, не готовая схема. Код заранее выдаёт разрешённые адреса и лимиты. Если предложение не прошло проверку, текст не должен обещать его игроку как свершившийся факт. Для новых деталей нужны ссылки на принятые сущности или отдельно публикуемые блоки; для старых событий сохраняется нынешняя проверка `event_seqs`.

Не пытаться доказать кодом каждую художественную фразу. Декоративные несостыковки допустимы по приоритету пользователя. У координат, владельцев предметов, существования NPC, исходов испытаний, наград и выполнения квестов должна быть однозначная фиксация.

## 10. Токены и стоимость

### 10.1. Факты текущего проекта

- В документации прогона интерпретатора 10 октября записано 162 309 / 12 758 и 144 026 / 9 987 токенов входа/выхода на 17 вызовов: в среднем примерно 9 548 и 8 472 входных токена. Это старый eval с суммарно 20 заявками на все случаи, а не замер реального раунда с двадцатью игроками.
- В `claudecli.Client` входные токены уже суммируются как обычный input + создание cache + чтение cache. Поэтому `TokensIn` не является количеством только новых, оплаченных по полной цене токенов.
- Защита рассказчика сейчас проверяет только `len(input) ≤ 60_000` байт переменной части. Системный промпт, JSON-схема, скрытые служебные расходы провайдера и ответ туда не входят. Потребуется настоящий общий бюджет роли/раунда и отдельный лимит ответа.
- Сам ответ с новым содержимым может стать главным растущим блоком: нужно ограничивать количество NPC, объектов, подходов и новых этапов, а не только размер входа.

### 10.2. Пример расчёта, не измеренный расход

В расчёте условно приняты: 20 игроков, 4 активных квеста, 20 событий; стабильная часть каждой роли 3 000 токенов; игрок 120 токенов в интерпретаторе / 80 у рассказчика; текущая клетка 400 / 300; короткий сосед 50; квест 180; событие 50; опорная память 300 на роль. Сценарий специально считает всех четырёх квестов, хотя в конкретную сцену часто достаточно передавать меньше.

| Сценарий | Вход двух обычных вызовов | Выход без достройки | Выход с подробностями новых клеток и одним новым квестом |
|---|---:|---:|---:|
| 20 игроков, 1 группа | около 14 140 | около 2 350 | около 3 400 |
| 20 игроков, 4 разошедшиеся группы | около 17 440 | около 2 650 | около 5 350 |

Для достройки дополнительно может потребоваться 0,5–2 тыс. входных токенов на задания и ограничения. Цель первого прототипа: примерно 14–20 тыс. входных и 2,4–5,4 тыс. выходных токенов на раунд в этих условиях. Это ориентир проектирования; без прогона на выбранной модели, служебной части Claude CLI и учёта повторов его нельзя выдавать за прогноз счета.

Формулы примера:

```text
I_interpreter = 3000 + 120×P + 400×G + 50×N + 180×Q + 300
I_narrator   = 3000 +  80×P + 300×G + 50×N + 180×Q + 50×E + 300
O_regular    = 70×P + 35×P + 100×G + 150
O_frontier   = O_regular + 400×G + 50×(3×G) + 500
P=20, Q=4, E=20, N=4×G в случае непересекающихся окрестностей
```

При 36 раундах за шесть часов с интервалом 10 минут вход в таком примере составляет примерно 0,5–0,7 млн токенов. Это показывает, почему бюджет следует проверять на сессию и мир, даже если один раунд помещается в контекст. Кэшированные токены, новые токены, ответ и денежную стоимость учитывать раздельно; для подписки также важны её реальные ограничения, которых из репозитория определить нельзя.

### 10.3. Что экономит

| Приём | Почему помогает |
|---|---|
| Короткие карточки соседей | четыре группы не отправляют двадцать полных сцен |
| Постоянные сущности и факт ID | знакомый NPC не описывается и не создаётся заново |
| Только текущий этап квеста подробно | четыре квеста не превращаются в двадцать четыре подробные локации |
| Адресная загрузка памяти | обещания и ключи сохраняются без всей истории |
| Одна пачка предложений на роль | нет отдельной системной части на каждого NPC/клетку/квест |
| Добавление подхода к существующему этапу | свободные действия не порождают новый квест каждый раз |
| Код для маршрутов, лимитов, условий, выдачи | модель не тратит ответ на расчёты и пересказ неизменных правил |
| Шаблоны для пустых клеток и повторного осмотра | нет повторной генерации «ничего полезного» |
| Частичное исправление плохого предложения | не нужно заново генерировать всю хронику и все клетки |
| Сохранённые пригодные ответы | повтор раунда не повторяет создание того же содержимого |

Начальные ограничения генерации: не более четырёх новых подробных клеток на раунд, по две интерактивные сущности и не более одного NPC в каждой; короткие карточки недостающих соседей; обычно один новый квест. Дополнительные подходы в уже известных сценах — небольшим отдельным бюджетом с объединением одинаковых запросов. Это предлагаемые лимиты прототипа, не универсальные числа качества.

### 10.4. Кэш

Claude Code автоматически использует кэширование префикса, а API различает новые входные токены, создание и чтение кэша. Кэш помогает повторяющейся системной части, но не заменяет сокращение динамического мира. Интервал раундов 10–60 минут может превышать пяти минутный TTL; нельзя закладывать гарантированный cache hit. В текущей официальной документации для `-p` в пределах включённой подписки описан TTL в час, для API/usage credits — по умолчанию пять минут; установленную версию и фактическое `usage` нужно проверить на стенде.

Источники: [Claude Code: prompt caching](https://code.claude.com/docs/en/prompt-caching), [Claude Platform: prompt caching и usage](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). Реальный выигрыш проверяется измерением, а не обещанием конкретного процента экономии.

## 11. Существенные риски и меры

| Риск | Последствие | Минимальная мера |
|---|---|---|
| Знакомые клетки и NPC создаются повторно | мир теряет идентичность | стабильные ID, координаты, стадии, повторное чтение |
| Генерация только после результата | новое действие не имеет реального эффекта в текущем раунде | локальные проекты подходов до движка, новая сцена после движка |
| Отдельный вызов на каждую клетку/квест | токены и задержка умножаются | одна общая пачка, короткие карточки |
| Четыре квеста на каждую группу/фракцию | лимит оказывается 8–16 квестов | на первом этапе общий лимит 4 |
| Сохранение всей карты в каждом снимке | рост БД, загрузки и времени replay | локальный снимок с адресными зависимостями |
| NPC/предмет объявлен текстом, но не принят | игрок взаимодействует с отсутствующей сущностью | публикация только после приёма содержимого |
| Квест требует уничтоженный единственный объект | весь набор квестов может зависнуть | цель этапа отделена от способа; восстановление будущего пути |
| Действия разных групп создают один объект дважды | повтор NPC, награды, клетки | уникальные ключи и единый приём пакета |
| Новые выходы соединены неправильно | недостижимый следующий этап | координаты и достижимость считает код |
| ИИ меняет цель задним числом | потеря смысла выполненных этапов | версии целей, изменения будущих этапов по событиям |
| Откат транзакции повторяет дорогую генерацию | лишняя трата и другой мир при повторе | идентификатор задания, сохранённый ответ и принятый пакет |
| Семантические ошибки при сложной общей схеме | повторы и потерянные действия | маленькие проекты, проверка ID/условий, сравнение моделей на eval |
| Неподготовленный генератор внезапно не работает | перемещение или обязательный сюжет блокируются | шаблонная клетка/квест, сохранение понятного итога каждой заявки |

Повторы HTTP/CLI нельзя обещать ровно один раз: после неоднозначного таймаута модель может уже выполнить запрос. Локальное сохранение результатов уменьшает повторные расходы, а идемпотентность записей предотвращает дубли мира. Это разные гарантии.

### 24. Данные динамического мира

- Статус: предложено.
- Цель: хранить изменяемый мир с постоянными ID и версией, сохраняя существующий событийный движок.
- Шаги: координаты и стадии в локации; записи объектов, переносимых предметов и минимальных NPC; стабильные ключи подходов; операции создания и обновления; новая схема снимка; сохранение по ID вместо индекса среза.
- Пакеты: `internal/model`, `internal/adapter/postgres`, `internal/service/engine`, `internal/app/round`, миграции.
- Критерий готовности: созданные сущности переживают перезапуск, одинаковые адреса не дублируются; создание и изменение воспроизводятся по сохранённым данным без ИИ; старые сохранения читаются по выбранной политике миграции.
- Проверка: два создания одной клетки, перенос предмета, изменение объекта, фиксация NPC и replay.

### 25. Сетка и исследование

- Статус: предложено.
- Цель: перемещаться по координатам без ручного создания каждого выхода.
- Шаги: `(0,0)` и четыре соседа; адреса и направления; seed местности; первое посещение; резерв соседей; возврат в готовую клетку; движение групп с существующим лимитом.
- Критерий готовности: после шести шагов по прямой ровно 23 уникальные клетки с окрестностью; повторный вход не создаёт новое место; два участника/группы дают одно первое открытие общей клетки.
- Проверка: движение по прямой, квадратный маршрут, возврат и две группы в одной точке.

### 26. Локальный контекст и память

- Статус: предложено.
- Цель: стоимость одного раунда зависит от участников и активных сцен, а не от возраста карты.
- Шаги: SQL-выборка окрестностей; адресные зависимости заявок и квестов; локальный снимок; короткие карточки соседей; компактная память именованных NPC и фактов; отдельные пакеты для интерпретатора и рассказчика; дедупликация клеток.
- Критерий готовности: для карты из 50 и 1 000 посещённых клеток при одинаковых активных сценах контекст остаётся примерно одинаковым; четырём удалённым группам передаются максимум 20 геометрических клеток в локальном окне плюс ограниченные адресные карточки удалённых зависимостей.
- Проверка: большое число сохранённых клеток, возвращение к старому NPC, важный факт вне последних трёх событий, отсутствие раскрытия скрытого содержимого.

### 27. Генерация содержимого мира

- Статус: предложено.
- Цель: новые места получают пригодное для движка содержимое в пределах бюджета.
- Шаги: интерфейс проекта содержимого; разрешённые координаты и ID; стадии короткой карточки и подробностей; небольшая схема NPC/объектов/подходов; валидация чисел, связей и лимитов; шаблон при сбое; фиксация результата задания.
- Критерий готовности: пустой адрес превращается в сохранённую сцену; опубликованные признаки не исчезают; модель не создаёт запрещённых выходов; невалидный пакет не объявляется игрокам как готовый мир.
- Проверка: неверные ID, превышение числа объектов, повтор задания, отказ модели, несколько новых клеток за один раунд.

### 28. Цели фракций и общие квесты

- Статус: предложено.
- Цель: мир поддерживает небольшое число автоматически возникающих линий с проверяемым прогрессом.
- Шаги: версии целей; квест/этап; условия достижения; скелет и ближайшая подробная цель; лимит 2+2; выдача по счётчику; один обязательный сюжетный; шаги и награды только по событиям; резерв координат будущих этапов.
- Критерий готовности: выдача дополнительных квестов на суммарных 1/3/7 новых клетках при выбранной политике; после освобождения одного слота четыре новых клетки; нет дублированной награды; минимум один сюжетный восстанавливается даже при сбое ИИ.
- Проверка: повторное посещение, открытие несколькими группами, завершение сразу нескольких квестов, лимит скрытых и открытых квестов, влияние смены цели на будущие этапы.

### 29. Влияние игроков и альтернативные пути

- Статус: предложено.
- Цель: свободный текст меняет механический способ решения и дальнейшее содержимое.
- Шаги: новые локальные подходы до движка; связывание с objective_key; предусловия и ограниченные эффекты; теги интереса; применение только к ещё не закреплённым деталям; восстановление заблокированного этапа; правила противоречащих проектов разных групп.
- Критерий готовности: одна цель достижима как минимум двумя разными действиями с различными последствиями; новое обоснованное действие разрешается в текущем раунде, а результат сохраняется; уничтожение единственного первоначального пути не блокирует все четыре квеста навсегда.
- Проверка: выбить/взломать/подкупить, обойти этап, разрушить объект, попросить предмет из текста без оснований, разные интересы групп.
- Ограничение: сложные конфликтующие действия и боевой PvP опираются на пункт 12; новый мир не заменяет его реализацию.

### 30. Генеративный рассказчик и фиксация

- Статус: предложено.
- Цель: рассказчик создаёт новые обстоятельства в контролируемом контракте и публикует только пригодный мир.
- Шаги: новая версия интерпретатора и рассказчика; стартовый пакет вместо одного текста `Opening`; совместный ответ с проектами; разделение существующих событий и новых деталей; атомарное применение принятого пакета и outbox; сохранение пригодных LLM-ответов по ключу задания; бюджет исправлений; новое решение восстановления вместо части ADR-0013.
- Критерий готовности: обычный успешный раунд использует два основных запроса; сбой и повтор не дублируют содержимое/награды; новые опубликованные NPC и объекты находятся в БД; replay не вызывает ИИ.
- Проверка: остановка после ответа ИИ до фиксации, два воркера, испорченный проект содержимого, неполная хроника, недоступность провайдера.
- Примечание: текущая транзакция с двумя вызовами может остаться временным решением первого среза при жёстких таймаутах; вынесение долгой генерации за блокировку требует явного состояния задания и проверки версии, а не простой перестановки функций.

### 31. Сквозные сценарии и бюджеты

- Статус: предложено.
- Цель: проверить масштабирование и игровую гибкость измерением.
- Шаги: фиксированные сценарии; набор для генерации и интерпретатора; 20 игроков/4 группы; 50 перемещений; возвращение в старую область; несколько конфликтующих интересов; сравнение двух общих запросов с редким отдельным генератором; учёт новых/cached токенов, выхода и исправлений; измерение SQL и объёма снимков.
- Критерий готовности: нет роста контекста пропорционально всей карте; нет потери принятых действий и повторной награды; зафиксированы p50/p95 задержки и токенов, доля исправлений, критерии качества; выбранная схема укладывается в согласованный бюджет.
- Проверка: чистые фейки для событий, интеграционные тесты БД, отдельный живой eval на выбранной модели. Не подменять живую оценку качества одной проверкой JSON-схемы.

## 13. Порядок внедрения

Первый вертикальный срез: одна группа, стартовая клетка и четыре коротких соседа, один сюжетный квест из трёх этапов, один NPC, два способа завершить один этап, возврат в знакомую клетку. Затем проверить четыре существующие группы, раскрытие побочных квестов и полноту лимитов. Это порядок проверки, а не отмена действующей поддержки групп.

Перед закрытой альфой интегрировать пункты 24–31 с пунктом 13 (нагрузка, NPC и бюджеты) и пунктом 12 (конфликты). Пункт 17 оставить как независимую будущую функцию личных целей. Пункт 21 об изображениях не является зависимостью текстовой карты.

## 14. Решения, которые нужно зафиксировать при реализации

| Вопрос | Рабочее допущение этого предложения |
|---|---|
| Лимит квестов на мир, фракцию или группу? | общий на мир: 2 сюжетных и 2 побочных |
| Первый сюжетный общий или свой у каждой фракции? | один общий, с разными последствиями для целей фракций |
| Кто знает о посещении/открытии? | общая видимость прототипа; скрытые будущие детали отдельно |
| Когда сбрасывается счётчик? | после принятия нового квеста и завершения старого; без запаса при полном лимите |
| Соседи подробно или коротко? | четыре короткие карточки, подробности при входе |
| Новые способы решения в том же раунде? | да, через принятый проект до движка |
| Можно ли менять основную цель? | по значимым событиям, с версией и сохранением выполненного |
| Отказа от квеста нет: как устранить тупик? | восстановление незавершённого пути или последствия, сохраняющие достижимую цель |
| Отдельный картограф? | геометрия только код; отдельный генеративный запрос выключен до сравнения eval |
| Сколько точности требуется? | строгие ID, состояния, владельцы, исходы и прогресс; свободнее декоративная проза |
