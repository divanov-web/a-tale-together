# ADR-0011: Рассказчик в транзакции раунда, проверка хроники кодом, деление сообщений при постановке в outbox

- Статус: принято
- Дата: 2026-10-10
- Область: `internal/service/narrator`, `internal/app/round`, `internal/service/engine`, `assets/prompts/narrator`, `cmd/eval-narrator`, `migrations/00012`

## Контекст
Пункт 09 вводит вызов 2 из 2 на раунд ([round-calls.md](../llm/round-calls.md)): публичные и локационные события → хроника в группу с блоком на сцену. Нужно решить, где выполняется вызов, как код гарантирует критерий «каждое значимое событие упомянуто, приватных фактов нет», откуда берётся связность между раундами, как длинная хроника проходит лимит Telegram без дублей при повторах доставки, и видит ли рассказчик исход проверки (движок пункта 07 писал `check_rolled` как приватное событие, а пример в round-calls.md передаёт его рассказчику).

## Варианты
| Вариант | За | Против |
|---|---|---|
| Рассказчик в той же транзакции, что заморозка и интерпретатор (ADR-0010) | один шаг, откат целиком при сбое процесса, повтор безопасен | блокировка игры на время второго вызова (десятки секунд на opus) |
| Отдельная транзакция после `published` | короче блокировка | второй статус восстановления, хроника может отстать от открытия следующего раунда |
| Проверка полноты: доверять модели | проще | нарушает критерий готовности и принцип 7 |
| Проверка полноты кодом: ID упомянуты, один дозапрос с замечаниями, остаток дописывает код | критерий выполняется всегда, модель получает адресную правку | строки кода в литературном тексте при повторном пропуске |
| Деление в адаптере Telegram при отправке | по месту лимита | одна строка outbox → несколько сообщений: при сбое середины повтор дублирует первые части |
| Деление при постановке в outbox (часть = строка с `part`) | дедуп и повтор по частям, `telegram_message_id` у каждой | лимит известен сценарию |
| Выжимка прошлых хроник из `messages_outbox` | без схемы | текст с подписями и подходами; outbox чистится |
| Ответ рассказчика в `rounds.narration` | чистый текст модели, пригоден для выжимки и eval | колонка и миграция |

## Решение
- Вызов рассказчика выполняется в `app/round.resolve` после свёртки событий, внутри транзакции заморозки (как ADR-0010). Сбой, таймаут, ответ не по схеме, превышение бюджета контекста (`narrator.MaxInputBytes`) или раскрытый секрет → шаблонная хроника пункта 07 с теми же подходами; мир не откатывается, `rounds.narration` пуст.
- `service/narrator`: контекст из состояния после раунда (`BuildInput`: сцены с присутствующими, описания персонажей как данные, видимые объекты и выходы, события только `public` и `location`, числа броска только в режиме «механика», подходы без шансов), системный промпт `assets/prompts/narrator/v1.md`, схема ответа `{chronicle, scenes[{location_id, party, text, event_seqs}]}`. Валидация: сцены из входа, `seq` из входа, пара событий перехода считается одним, скрытые описания не встречаются в тексте, в «повествовании» нет цифр, объём в границе. Замечания → один дозапрос с полным повтором ответа; оставшиеся пропуски дописываются кодом строкой события (`Narration.Patched`), оставшаяся утечка → `ErrLeak` → шаблон.
- Подходы следующего раунда считает код (`narrator.Options`: видимые объекты, сложность по пресету режима плюс локация, шанс каждого присутствующего по пулу) и приписывает к сцене строкой `narrator.OptionsText`; модель их не меняет.
- Ответ рассказчика хранится в `rounds.narration jsonb` (миграция `00012`); выжимка последних трёх хроник (`RecentNarrations`) идёт в контекст следующего вызова.
- Событие `check_rolled` получает видимость `location`: попытка и её исход видны присутствующим и рассказчику; факт, состояние и HP остаются приватными.
- Хроника делится на части по лимиту Telegram при постановке в outbox (`app/round.splitParts`, часть = строка `messages_outbox` с `part` 1..N, подпись «(продолжение)» у частей после первой); адаптер Telegram текст не делит.
- Оценочный набор `assets/prompts/narrator/eval/cases.json` (10 случаев: пример round-calls, секреты, инструкции в описании, режимы, смерть и возврат, статусы, удержание группы, связность), прогон `make eval-narrator` на живом `claude-cli`; проходит случай, в котором модель упомянула все события сама и не нарушила запреты.
