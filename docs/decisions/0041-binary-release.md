# ADR-0041: Релиз бинарником с домашней машины вместо сборки на сервере

- Статус: принято (уточняет ADR-0040)
- Дата: 2026-10-17
- Область: `deploy/release.sh`, `cmd/bot` (флаги `-migrate`, `-migrate-status`), `internal/adapter/postgres/migrate.go`, `docs/dev/server.md`, скилл `/tale-release`

## Контекст
ADR-0040 выкатывал бота сборкой на сервере (`git reset --hard origin/master`, `make build`, goose). Сервер — 1 vCPU, 1 ГБ ОЗУ, 10 ГБ диска: компиляция идёт параллельно с ботом и VPN и упирается в swap, кэши Go заняли 1.4 ГБ из 1.3 ГБ оставшихся, на сервере приходится держать Go, git и goose. Руководитель попросил скилл релиза, который выполняется только по его команде и включает миграции, ручные правки таблиц и перезапуск.

## Варианты
| Вариант | За | Против |
|---|---|---|
| Сборка на сервере из `origin/master` (ADR-0040) | код на сервере равен GitHub, одна команда | минуты сборки на 1 vCPU, лаги бота, 1.4 ГБ кэшей, toolchain на проде |
| Сборка дома, бинарник по ssh | WSL и сервер — linux/amd64, статический файл, секунды на выкат, откат заменой файла, Go на сервере не нужен | на сервере может оказаться код не из репозитория; зависимость от домашней машины |
| GitHub Actions собирает и выкатывает | без домашней машины | ssh-ключ и секреты в GitHub, лишнее для одного разработчика; схема переносится позже без изменений на сервере |

## Решение
- Релиз выполняет `deploy/release.sh` с домашней машины по шагам `check build upload stop migrate switch start verify` (`all`), плюс `status`, `rollback`, `clean`; обёртка `make release RELEASE_ARGS=...`. Запуск только по команде руководителя через скилл `/tale-release`; во время разработки Claude релизы не делает.
- Защита от кода вне репозитория: `check` отказывает при грязном дереве и если HEAD не входит в `origin/master`. Порядок остаётся: руководитель пушит, Claude релизит; версия в `bot starting` и `/ping` равна хешу на GitHub.
- Бинарник `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`, `-trimpath -s -w`, около 17 МБ, шаблоны, промпты и миграции встроены (`go:embed`). На сервере `releases/bot-<версия>`, рабочая ссылка `bin/bot` (путь юнита не меняется), прежняя цель в `releases/.previous`.
- Миграции применяет сам бинарник: `bot -migrate` (при остановленном сервисе, читает `.env` сервера), `bot -migrate-status`; goose CLI на сервере не нужен. `MIGRATE_ON_START=false` на проде сохраняется: между миграциями и запуском Claude при необходимости правит строки запущенных игр SQL, как дома.
- `rollback` возвращает бинарник, не базу; откат схемы — только через `pg_restore` из ежедневного бэкапа по подтверждению руководителя.
- На сервере остаются `.env`, `bin/`, `releases/`, `deploy/` (копии юнита, logrotate и бэкапа, ставятся на шаге `start`), `logs/`; клон репозитория, Go, goose и кэши удаляются после первого релиза по новой схеме. `deploy/deploy.sh` удалён.

- Домашний скилл `/home-fornex`: действие `deploy` заменено на вызов `/tale-release`, `make` на сервере больше не используется.
