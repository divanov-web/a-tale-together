# ADR-0010: Интерпретатор внутри транзакции заморозки, безопасное толкование кодом

- Статус: принято
- Дата: 2026-10-10
- Область: `internal/service/interpreter`, `internal/app/round`, `assets/prompts`, `cmd/eval-interpreter`, `.claude/rules/llm.md`

## Контекст
Пункт 08 вводит вызов 1 из 2 на раунд ([round-calls.md](../llm/round-calls.md)): все заявки одним запросом к модели → намерения. Вызов длится секунды, иногда десятки секунд. Разрешение раунда (пункт 07) идёт в одной транзакции с заморозкой под `LockGame`. Нужно решить, где выполняется вызов модели, что происходит при её сбое и где живёт безопасное толкование непонятной заявки (G3).

## Варианты
| Вариант | За | Против |
|---|---|---|
| Вызов модели внутри транзакции заморозки (статусы `frozen` → `published` в одной транзакции) | один шаг, повтор после сбоя процесса безопасен: транзакция откатывается целиком, раунд снова `open` с прошедшим дедлайном; второй экземпляр не возьмёт игру (`SKIP LOCKED`) | блокировка строки `games` на время вызова; соединение с БД занято |
| Две транзакции: заморозка (`frozen`), вызов модели снаружи, затем разрешение (`resolving` → `published`) | короткие транзакции | нужен сторож от повторного взятия игры планировщиком во время вызова; больше состояний для восстановления |
| Безопасное толкование в движке (`ambiguous` при любых неоднозначностях) | движок видит всё | игрок теряет раунд из-за одной непонятной фразы; противоречит решению руководителя |
| Безопасное толкование в интерпретаторе: `fallback` модели или `wait`, движок разрешает как обычное действие | у каждой заявки осмысленный итог; непонятное видно в итоге | статус `ambiguous` остаётся только для намерения без типа |

## Решение
- Вызов интерпретатора выполняется внутри транзакции заморозки (`app/round.resolve` → `interpret`). `Submit`, `Info` и `/status` строку игры не блокируют, после дедлайна заявки на этот раунд всё равно не принимаются; таймаут вызова — из профиля (`timeout_seconds`, по умолчанию 120 с). Две транзакции и статус `resolving` откладываются до появления реальной нагрузки.
- `service/interpreter`: сборка контекста из снимка v2 (`BuildInput`: только видимые объекты и выходы, персонажи без секретов, последние 3 знания), системный промпт `assets/prompts/interpreter/v1.md` через `embed`, JSON-схема ответа, валидация по снимку и модели персонажа, один повтор с перечнем ошибок, затем безопасное толкование (`fallback` модели, если он проходит проверку и относится к `explore`/`wait`/`move`, иначе `wait`). Пропущенная заявка → `wait`.
- Намерение с непустым типом и `Ambiguities` разрешается движком как обычное действие, в итоге дописывается «безопасное толкование: …»; `ambiguous` получает только намерение без типа.
- Сбой или таймаут модели, ответ не по схеме, отсутствие профиля → `interpreter.Fallback`: `rules.ParseTyped` для типовых команд, остальное `wait` с причиной; раунд публикуется.
- Свободное испытание: модель назначает характеристику, навык, риск и эффекты (`on_success`: `fact`, `move`, `reveal` существующего скрытого объекта; `on_fail`: `condition` из списка, `damage` ≤ 2, `fact`); движок назначает сложность по таблице риска плюс локация, бросает и применяет ветвь. Состояние объектов меняется только подходами из данных локации. Переход с испытанием (`move` + характеристика) при провале оставляет персонажа на месте.
- Оценочный набор `assets/prompts/interpreter/eval/cases.json`, прогон `make eval-interpreter` на живом `claude-cli`; результаты в `docs/llm/README.md`.
