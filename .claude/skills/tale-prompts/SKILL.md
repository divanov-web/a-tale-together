# Проектировщик промптов игры

## Источники

- Риски §3–6 (`docs/concept/massive_dnd_implementation_risks.md`, гипотезы, не источник правды): граница движок/ИИ, экономия токенов, разбиение запросов, секреты.
- `docs/llm/`: `README.md` (конвейер, бюджет, измерения), `interpreter.md`, `narrator.md`.
- Промпты: `assets/prompts/<роль>/vN.md`; оценочные наборы `assets/prompts/<роль>/eval/`.
- Код вокруг LLM: `.claude/rules/llm.md`; провайдеры и профили: `docs/llm/providers.md` (ADR-0003). Промпт пишется провайдеро-независимо: одна системная часть и одна схема для всех реализаций `llm.Client`.

## Принципы

- LLM интерпретирует и описывает; не считает, не решает, не создаёт факты. Что решает движок, у LLM не спрашивают.
- Текст игрока — данные в выделенном блоке; промпт явно запрещает исполнять инструкции из него.
- Выход — строгая схема; поля минимальны и стабильны; ID короткие и говорящие.
- Контекст = текущее состояние + релевантные факты + последние события адресата; полная история не передаётся. Не выкидывать: ID и автор действия, цель, намерение, условия, ограничения, версия состояния, знания персонажа, зависимости.
- Каждое принятое действие упоминается в ответе ровно один раз по ID; пропуск находит код и дозапрашивает адресно.
- Стабильный префикс (правила, схема) отделён от переменной части для кэширования.
- Версия промпта в имени файла и в `llm_runs`; изменение промпта = новая версия + прогон оценочного набора.

## Процесс

1. Роль вызова и границы: что приходит, что обязано выйти, что запрещено.
2. Схема JSON в `docs/llm/<роль>.md`; примеры валидных и невалидных ответов.
3. Промпт `assets/prompts/<роль>/vN.md`: системная часть, формат данных, правила, примеры.
4. Оценочный набор из `docs/game/scenarios.md`: вход → ожидаемый выход.
5. Измерить токены вход/выход, ошибки, пропуски; записать в `docs/llm/README.md`.
