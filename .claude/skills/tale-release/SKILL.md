# Релиз на прод

Схема: ADR-0041. Бинарник собирается дома и уходит на сервер по ssh; на сервере нет Go, git и goose, миграции применяет сам бинарник (`bot -migrate`). Сервер и его команды: `docs/dev/server.md`; доступы и состояние машины — проект «Дом», карточка `fornex`, скилл `/home-fornex`. Скрипт: `deploy/release.sh <шаг ...>` (шаги в шапке скрипта), обёртка `make release RELEASE_ARGS="..."`.

## Правила

- Релиз только по явной команде руководителя в этом диалоге. Завершение задачи, зелёные тесты, просьба «проверь на сервере» релизом не являются (решение руководителя 2026-10-17). Во время разработки Claude релизы не инициирует и не предлагает их как шаг задачи.
- Выкатывается только то, что есть в `origin/master`: `check` отказывает при грязном дереве и при HEAD вне `origin/master`. Если push не сделан, попросить руководителя сделать `git push` и ждать; самому `git push` не делать.
- На сервере один экземпляр бота в systemd: `make start/stop/restart` там не используются, только шаги скрипта и `systemctl`.
- Миграции на проде применяются при остановленном сервисе и не откатываются: `rollback` возвращает бинарник, не базу. Миграция с удалением или переименованием колонки требует отдельного плана и подтверждения руководителя.
- Секреты (`.env` сервера, токен, пароль базы) на экран не выводить.
- Перед релизом дома должны быть пройдены `make test` и `make lint` текущей версии; если задача завершалась без них, прогнать.

## Порядок: обычный релиз (`all`)

1. `make release RELEASE_ARGS=check`: версии дома и на сервере, коммиты и миграции к выкату. Прочитать список миграций: если среди них есть изменение `settings` игр, `app_settings`, `llm_profiles` или колонок с умолчаниями, которые должны распространиться на уже идущие игры, перейти к сценарию «с ручными правками».
2. Если на сервере идёт игра и релиз меняет раунд или доставку, предупредить руководителя о паузе в несколько секунд; раунд на границе остановки не теряется (outbox, идемпотентность), но лучше релизить вне момента закрытия раунда (`/round` в проде или `select deadline_at from rounds where status='open'`).
3. `make release RELEASE_ARGS=all`: `check build upload stop migrate switch start verify`. Любой шаг с ошибкой останавливает скрипт; дальше по таблице диагностики.
4. Проверка руками: `/ping` в прод-боте отвечает новой версией (делает руководитель, Claude напоминает). Лог: `ssh fornex-dev 'tail -n 30 ~/Projects/a-tale-together/logs/bot.log'`.
5. Строка в `docs/dev/releases.md` (дата, версия, миграции, ручные правки, замечания), коммит, отчёт: версия до и после, применённые миграции, правки таблиц, состояние памяти из `verify`.

## Порядок: релиз с ручными правками таблиц (`manual`)

1. `make release RELEASE_ARGS="check build upload stop migrate"`. Сервис остановлен, схема новая, бот ещё старый по ссылке `bin/bot`.
2. SQL на прод-базе под `divanov`: `ssh fornex-dev "psql \"\$(grep ^DATABASE_URL= ~/Projects/a-tale-together/.env | cut -d= -f2-)\" -v ON_ERROR_STOP=1 -c '<sql>'"`. Правила те же, что дома в `/tale-env apply`: умолчания новых ключей `settings` для запущенных игр, значения прод-режима (не dev: кворум и длительность раунда прод-овые), `UPDATE` с `WHERE` по конкретным `game_id`, перед `UPDATE` показать `SELECT` затронутых строк. Сначала проверить, не сделала ли это уже миграция.
3. `make release RELEASE_ARGS="switch start verify"`, далее шаги 4–5 обычного релиза; SQL целиком в строку журнала релизов.

## Откат

`make release RELEASE_ARGS=rollback`: стоп, `bin/bot` на прежний бинарник из `releases/.previous`, старт, проверка. База остаётся с новыми миграциями, поэтому откатывать можно только если старый код с новой схемой совместим (добавленные колонки и таблицы — да). Иначе сначала `pg_restore` из `/var/backups/tale` по `/home-fornex restore` (опасное действие, подтверждение руководителя), потом откат бинарника.

## Статус без релиза

- `make release RELEASE_ARGS=check` — что накопилось к выкату (ничего не меняет на сервере, кроме `git fetch` дома).
- `ssh fornex-dev '~/Projects/a-tale-together/bin/bot -migrate-status'`, `systemctl status tale-bot`, лог — `/home-fornex status | bot | logs | db`.

## Диагностика

| Симптом | Действие |
|---|---|
| `рабочее дерево не чистое` | закоммитить файлы задачи или отложить правки; релиз из грязного дерева запрещён |
| `HEAD ... не входит в origin/master` | руководитель делает `git push`, затем повторить |
| `verify`: нет `bot starting` с новой версией | `ssh fornex-dev 'systemctl status tale-bot; tail -n 40 ~/Projects/a-tale-together/logs/bot.log'`; ошибка конфигурации или миграции → исправить дома новым коммитом, не на сервере; бот не поднимается → `rollback` |
| `migrate` упал | лог ошибки goose; миграцию не править, писать новую (правило `rules/postgres.md`); сервис остановлен — либо `switch start` старой версии через `rollback`, либо срочная миграция-исправление |
| `409 Conflict` в логе | второй экземпляр с тем же токеном (домашний `.env` с прод-токеном?); `pgrep -a bot` на сервере и дома |
| память: занято больше 800 МБ после старта | проверить зависшие процессы `claude` на сервере (`pgrep -a claude`); ограничение 1 ГБ ОЗУ, см. `docs/dev/server.md` |
| `scp`/`ssh` не подключается | плейбук «Нет связи» в `/home-fornex` |

## Переход со старой схемы (один раз)

Первый релиз по этой схеме переводит сервер с клона и `make build` (ADR-0040) на бинарники: `switch` переносит собранный там `bin/bot` в `releases/bot-old-<дата>` и ставит ссылку. После успешной проверки освободить диск на сервере по команде руководителя: удалить `~/go`, `~/.cache/go-build`, `~/.local/go`, `~/.local/bin/goose` и из `~/Projects/a-tale-together` всё, кроме `.env`, `bin/`, `releases/`, `deploy/`, `logs/` (около 1.7 ГБ). Записать в карточку `fornex` через `/home note`.
